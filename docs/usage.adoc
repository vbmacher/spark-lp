= Using spark-lp
:toc: left
:source-highlighter: highlightjs

spark-lp is an optimization solver built for Apache Spark. It provides a Scala 2.12 modelling API for
linear, mixed-integer linear and supported quadratic models. Your application supplies Spark
(supported: 2.4.8 and 3.0.2–3.5.3 — test the version you deploy). Depend on the
`com.github.vbmacher:spark-lp` artifact, whose versions follow the `<spark-version>_<library-version>`
scheme (for example `3.5.3_2.1.0`); pick one matching your Spark version. Native BLAS/LAPACK
(optimized linear-algebra libraries) can improve performance; the Java implementation also works.

This guide starts with the modelling API, then covers solving, diagnostics,
interchange and tuning.

== A quick example

fat, fibre and salt requirements. Runnable source is in the
https://github.com/vbmacher/spark-lp/tree/master/examples/src/main/scala/com/github/vbmacher/spark_lp/examples[examples module],

[#_modelling_with_the_dsl]
== Modelling with the Scala API

Import the modelling API, create an `LpProblem`, declare its decision variables, add constraints and an objective,
then call `solve()`:

[source,scala]
----
import com.github.vbmacher.spark_lp.dsl._
import com.github.vbmacher.spark_lp.dsl.implicits._

val model = LpProblem("production", Minimize)
----

This guide uses these terms:

[cols="1,3",options="header"]
|===
|Term |Meaning
|Decision variable |A value chosen by the solver. `LpVariable` represents one variable.
|Variable set |An `LpVariableSet[K]` containing one variable for each unique key `K` in Spark data.
|Key |The application value that identifies one variable in a variable set, such as a product ID.
|Bound |The smallest or largest value allowed for a variable.
|Variable type |`Continuous`, `Integer` or `Binary`. The API parameter is named `category`.
|Integrality |The requirement that `Integer` and `Binary` variables have whole-number values.
|Objective |The numeric expression that the solver minimizes or maximizes.
|Constraint |A required `<=`, `>=` or equality relationship between an expression and a value.
|Coefficient |The numeric multiplier of a variable in an expression.
|Linear expression |A sum of constants and variables multiplied by numeric coefficients.
|Feasible |Satisfies every variable bound and constraint within the configured tolerance.
|Tolerance |A small numeric allowance used when comparing floating-point values.
|Objective gap |The difference between the best feasible objective found and the best possible objective still allowed by unfinished integer search.
|Residual |A numeric error measure; smaller values are better and zero means exact agreement.
|Presolve |Automatic model simplification performed before numerical optimization.
|Driver |The Spark application process that coordinates distributed work.
|Executor |A Spark process that runs distributed tasks.
|RDD |Spark's distributed collection type.
|LP |Linear program: a model with a linear objective and linear constraints.
|QP |Quadratic program: a model with a quadratic objective and linear constraints.
|MIP |Mixed-integer program: an LP containing `Integer` or `Binary` variables.
|===

=== Declaring variables

[cols="2,2,2",options="header"]
|===
|Call |Use |Return value
|`model.variable("x")` |Declare one variable. |`LpVariable`
|`model.variables("x", df, $"id")` |Declare one variable for each unique, non-null DataFrame key. Use `struct(...)` for a key made from multiple columns. |`LpVariableSet[Row]`
|`model.variablesOf("amount", offers, (offer: Offer) => offer.id)` |Declare one variable for each unique, non-null typed `Dataset` key. |`LpVariableSet[Offer]`
|`model.indexedVariables("x", Seq("a", "b"))` |Declare a small variable set from keys already held on the driver. |`LpLocalVariables[String]`
|`model.matrixVariables("flow", origins, destinations)` |Declare one local variable for each `(origin, destination)` pair. |`LpLocalVariables[(Origin, Destination)]`
|===

All five methods accept `lowerBound`, `upperBound` and `category`. Their defaults declare a continuous
variable with `0.0` as its lower bound and no upper bound.

Use `variables` or `variablesOf` when Spark holds the keys. Use `indexedVariables` or `matrixVariables`
only for small local collections: these methods create every `LpVariable` object on the driver.
`indexedVariables` preserves key order; `matrixVariables` iterates the first input before the second.

Access one variable in a set with `variables(key)`. The returned `LpVariable` can be used in expressions and with
`solution.value`. Repeating the same lookup refers to the same variable. Primitive and tuple keys work
without configuration; define an `LpKeyEncoder` for another key type. Null and duplicate keys are errors.

[#_variable_bounds_categories_and_fixing]
=== Variable bounds, types and fixing

[cols="1,3",options="header"]
|===
|`category` value |Allowed values
|`Continuous` |Any `Double` within the declared bounds.
|`Integer` |Whole numbers within finite declared or solver-inferred bounds. Finite endpoints must be between `-(2^53 - 1)` and `2^53 - 1`.
|`Binary` |`0` or `1`, further restricted by the declared bounds.
|===

`lowerBound` is inclusive. `upperBound = Some(value)` sets an inclusive upper bound; `None` leaves it
unbounded. Equal bounds fix a variable. Use `Double.NegativeInfinity` as the lower bound for a variable
with no lower limit.

[cols="2,3",options="header"]
|===
|API |Effect
|`variable.setBounds(lower, upper)` |Replace both bounds and discard bounds saved by an earlier `fix`.
|`variable.fix(value)` |Set both bounds to `value`. The first call saves the bounds restored by `unfix`.
|`variable.unfix()` |Restore the saved bounds. Do nothing if `fix` has not saved bounds.
|`variable.rename(name)` |Change the name shown by inspection, export and result APIs.
|`variable.lowerBound`, `variable.upperBound` |Read the current bounds.
|===

These methods are available on one variable, an entire `LpVariableSet`, or one selected variable. They
return the same `LpVariable` or `LpVariableSet`, so existing expressions remain valid. Edits apply to
later solves; they do not change an existing `LpSolution`. Editing while a solve is active is rejected.

[source,scala]
----
val capacity = model.variable("capacity", upperBound = Some(100.0))
capacity.setBounds(0.0, Some(80.0)).fix(40.0).rename("available_capacity")
capacity.unfix() // restores [0,80]
// A variable set uses the same operations: allocation(("region", 1)).fix(5.0)
----

=== Building linear expressions

[cols="1,2",options="header"]
|===
|Expression |Meaning
|`x + 2.0 * y` |A linear expression. Multiplying two variables is unsupported.
|`amount.sum` |Sum every variable in `amount`.
|`amount.sum($"cost")` |Multiply each variable by the `cost` column from the DataFrame used to declare `amount`, then sum.
|`amount.sumBy("region")()` |Build one sum for each `region` value.
|`amount.sumBy("region")($"cost")` |Build one cost-weighted sum for each `region` value.
|`lpSum(...)`, `lpSumBy(...)` |Build the same sums with standalone functions.
|`x / 2.0`, `(2.0*x + y + 4.0) / -2.0` |Divide one variable or expression by a finite nonzero constant.
|`lpDot(Seq(2.0, 3.0), Seq(x, y))` |Build `2.0*x + 3.0*y` from local collections of equal length.
|===

Multiplying two variables is unsupported. Division requires a finite, nonzero divisor. `lpDot` requires
finite coefficients and collections of equal length. Use `sum`, `sumBy`, `lpSum` or `lpSumBy` for data
held by Spark; `lpDot` operates on local collections.

For `Dataset[Offer]`, use `lpSum(amount.weightedBy(offers)(_.cost))`. For coefficients stored in a
different DataFrame, use
`lpSumBy(amount.terms(coefficients, Seq($"region"), $"coefficient"), Seq("region"))`. The coefficient
DataFrame must contain the variable key, each grouping column and the coefficient column. Repeated rows
for the same group and variable are added.

=== Adding constraints

Create a constraint with `expression <= rhs`, `expression >= rhs` or `expression === rhs`, then add it
with `model += constraint`. Use `===`; Scala's `==` returns a `Boolean`. Use
`constraint.named("capacity")` to give the constraint a stable name for diagnostics and export.

For grouped expressions, a numeric right-hand side applies to every group. A grouped right-hand-side
DataFrame must contain the grouping columns and one numeric `rhs` value per group. Every expression group
must have an `rhs`. An `rhs` group with no expression terms creates a constant-only constraint.
`constraint.withRhs(value)` returns a new constraint; it does not alter one already added to the model.

[#_setting_the_objective_and_feasibility_models]
=== Setting the objective (or solving without one)

`LpProblem("name")` minimizes by default. Pass `Maximize` as the second argument to maximize.

[cols="2,3",options="header"]
|===
|API |Effect
|`model += expression` |Set the objective. Fails if the model already has one.
|`model.setObjective(expression)` |Set or replace the objective.
|===

If no objective is set, `solve()` searches for values that satisfy the constraints and uses the constant
objective `0.0`. The objective remains unset, so it can be added before a later solve.

=== Convex quadratic objectives

[cols="2,3",options="header"]
|===
|API |Objective term
|`QpObjective.squaredDeviation(x, target, weight)` |`weight * (x - target)^2`
|`QpObjective.squared(expression, weight)` |`weight * expression^2`
|`QpObjective.sumSquares(terms)` |The sum of `(expression, weight)` squared terms.
|`QpObjective.separable(diagonal, linear)` |A quadratic objective with no cross-variable products. A coefficient `d` for variable `x` in `diagonal` contributes `0.5*d*x^2`; `linear` supplies the ordinary linear expression and constant.
|===

Quadratic objectives support continuous variables only. Quadratic constraints are unsupported. A
minimization objective must be convex (curve upward); a maximization objective must be concave (curve
downward). `squared`, `sumSquares` and nonnegative weights construct convex minimization terms.

[source,scala]
----
import com.github.vbmacher.spark_lp.dsl._
import com.github.vbmacher.spark_lp.dsl.implicits._

val model = LpProblem("fit")
val x = model.variable("x", lowerBound = -3.0, upperBound = Some(4.0))
model += QpObjective.squaredDeviation(x, target = 2.0, weight = 3.0)
val result = model.solve()
try println(result.value(x)) finally result.close()
----

Combine terms before adding the objective, for example:
`model += QpObjective.squared(x + 2.0 * y - 5.0) + QpObjective.squared(x - y - 1.0)`. See
xref:algorithm.adoc#_convex_quadratic_objectives[the QP guide] for representations, transformations and
limits.

=== Special ordered sets

Special ordered sets restrict which variables may be nonzero:
`SOS1` and `SOS2` are the two supported special ordered set types.

[cols="2,3",options="header"]
|===
|API |Rule
|`model.addSos1("selection", Seq(x -> 1.0, y -> 2.0))` |At most one listed variable may be nonzero.
|`model.addSos2("sequence", members)` |At most two listed variables may be nonzero, and they must be adjacent after sorting by weight.
|===

Every listed variable needs finite lower and upper bounds. SOS1 weights must be finite; SOS2 weights must
also be unique. Continuous, integer and binary variables are accepted, but quadratic objectives with SOS groups are
not. `MipConfig.sosZeroTolerance` controls when the solver treats a value as nonzero; the default is
`1e-6`. JSON preserves SOS groups. LP and MPS export do not support them.

=== Combinations and permutations

`LpCombinatorics` builds local key collections for small combinatorial models:

[cols="2,3",options="header"]
|===
|API |Result
|`combinations(values, size)` |Each unordered selection of `size` input positions.
|`permutations(values, size)` |Each ordered selection of `size` input positions.
|`combinationsUpTo(values, maximumSize)` |Combinations of every size from `0` through `maximumSize` or the input length.
|`permutationsUpTo(values, maximumSize)` |Permutations of every size from `0` through `maximumSize` or the input length.
|===

The methods return lazy `Iterator[Vector[A]]` values. Size `0` produces one empty vector; a fixed size
larger than the input produces no values; a negative size fails. Equal input values at different positions
remain distinct inputs.

[source,scala]
----
val pairs = LpCombinatorics.combinations(Vector("a", "b", "c"), 2)
val choices = pairs.map { pair =>
  model.variable(pair.mkString("pair_", "_", ""), category = Binary)
}.toVector
model += (lpSum(choices.map(x => 1.0 * x)) >= 1.0)
----

The input must already be local. The result is lazy, but the number of results can still be very large.

=== Inspecting and editing expressions

[cols="2,3",options="header"]
|===
|API |Result
|`expression.constant` |The constant term. No Spark action.
|`expression.coefficients` |An `RDD[LpCoefficient]` containing the nonzero variable coefficients. Repeated terms are added.
|`expression.coefficient(variable)` |One coefficient, or `0.0` if the variable is absent. Performs a Spark action.
|`expression.withCoefficient(variable, value)` |A new expression with that coefficient replaced.
|`expression.withoutCoefficient(variable)` |A new expression without that variable.
|`expression.withConstant(value)` |A new expression with that constant.
|===

The `with...` methods do not change the original expression. Variables must belong to the same model, and
new numeric values must be finite.

=== Copying a model into scenarios

`val scenario = model.copy("scenario")` returns an `LpModelCopy`. It contains an independently editable
`scenario.model` with the same declarations, constraints, objective and optimization direction.

[cols="2,3",options="header"]
|===
|API |Return value
|`scenario.variable(x)` |The copy of individually declared or selected variable `x`.
|`scenario.variables(amounts)` |The copy of variable set `amounts`.
|`scenario.expression(expression)` |The same expression rebound to copied variables.
|===

The copy shares the original lazy DataFrame and Dataset inputs; it is not a copy of their rows. Store
changing inputs in stable storage before solving either model when both must read identical data.

== Solving and reading results

`model.solve()` uses the built-in solver. `model.solve(config)` applies a `SolveConfig`. Both return an
`LpSolution`.

An `LpSolution` may contain a candidate assignment (a value for every decision variable). Check
`solution.candidate` before reading values:

[cols="1,3",options="header"]
|===
|Field |Meaning
|`available` |The solution contains variable values.
|`feasible` |Those values satisfy the original bounds and constraints within the configured tolerance.
|`iteration` |The continuous-solver iteration that produced the retained values, when applicable.
|===

[cols="1,3",options="header"]
|===
|Status |Interpretation
|`Optimal` |The solver accepted the result within its numerical tolerances. For integer models, the remaining objective gap is within the configured limit.
|`IterationLimit` |A continuous-iteration or integer-search limit was reached. Inspect `candidate` before using values.
|`Stopped` |A time limit, callback request or stagnation rule (a stop after repeated lack of progress) stopped the solve. Inspect `stopReason` and `candidate`.
|`Infeasible` |The solver proved that no assignment satisfies the model within its tolerance.
|`Unbounded` |The objective can improve without limit and the result includes a feasible assignment.
|`InfeasibleOrUnbounded` |The objective can improve without limit, but the solver did not establish a feasible assignment.
|===

[cols="2,3",options="header"]
|===
|API |Result
|`solution.value(x)` |The `Double` value of one variable.
|`solution.values(amount)` |The DataFrame used to declare `amount`, plus `lp_variable` and `lp_value` columns.
|`solution.objectiveValue` |The objective evaluated at the retained assignment, or the status-specific infinite/`NaN` value.
|`solution.constraints` |A DataFrame with one diagnostic record per original constraint.
|===

`solution.constraints` has these columns:

[cols="1,3",options="header"]
|===
|Column |Meaning
|`name` |Constraint name.
|`group` |Grouping key, or `null` for an individually declared constraint.
|`activity` |Value of the left-hand expression.
|`sense` |`<=`, `>=` or `==`.
|`rhs` |Right-hand-side value.
|`slack` |`rhs - activity` for `<=` and equality; `activity - rhs` for `>=`. A negative inequality slack is a violation.
|`dual` |Optional shadow price, described below.
|`note` |Presolve or result note.
|`dual_note` |Reason why `dual` is unavailable, or `null` when it is available.
|===

`LpModelException` flags invalid input, including a contradictory constant-only constraint.
`LpNumericalException` flags a failed solve, not a proof of infeasibility. Invalid solver settings throw
`IllegalArgumentException` before computation.

`LpSolution` owns cached Spark data. Complete calls to `values`, `constraints`, `evaluate`, evidence APIs,
and other result DataFrames or RDDs before `solution.close()`. Closing releases the solution's cached data;
it does not delete checkpoint files or caller-owned caches.

Set `spark.sparkContext.setCheckpointDir(checkpointUri)` before solving. In a cluster, use storage that
every executor can reach, such as HDFS (Hadoop Distributed File System) or Amazon S3. A later `solve()` reads lazy model inputs again; cache
or write changing inputs to stable storage when repeated solves must use identical data.

See xref:algorithm.adoc[how the solver works] for implementation details and numerical behavior.

[#_solve_evidence_and_certificates]
=== Evidence for infeasible or unbounded results

`solution.evidence` is an `Option` containing a proof for an `Infeasible`, `Unbounded`, or
`InfeasibleOrUnbounded` result when the solver produced one. `proof.verify(tolerance)` recomputes the proof
checks from stored coefficients and bounds and returns a report with `valid`, `residual` and `margin`.

[source,scala]
----
val solution = model.solve()
try {
  solution.evidence.foreach { proof =>
    val checked = proof.verify(tolerance = 1e-7)
    println(s"valid=${checked.valid} residual=${checked.residual} margin=${checked.margin}")
  }
} finally solution.close()
----

Evidence is numerical and tolerance-dependent. See
xref:algorithm.adoc#_verifying_solve_evidence[certificate verification] for each proof type and sign
convention.

=== Evaluating expressions against a solution

`solution.evaluate(3.0 * x + amount.sum($"cost") + 7.0)` returns the expression value for the retained
assignment. It performs Spark work and returns one `Double` to the driver. The expression must use the
same model and only variables that existed when the solution was created. An unavailable candidate or a
closed solution is rejected. Evaluating an infeasible candidate is a calculation, not a feasibility claim.

=== Final solve timings

Every `LpSolution` exposes `timings: LpSolveTimings`. Values are seconds measured by a monotonic clock.

[cols="1,3",options="header"]
|===
|Field |Scope
|`compilationWallSeconds` |Validation, derivation of missing bounds, presolve and conversion from the public model to solver input.
|`numericalSolveWallSeconds` |The continuous solve or the complete integer search.
|`resultReconstructionWallSeconds` |Conversion from solver output to the public result and its stored Spark data.
|`totalWallSeconds` |Wall time from `solve` entry until the returned result is ready.
|`driverProcessCpuSeconds` |Optional processor time used by the Java driver process over the same interval. This excludes executor and cluster processor time.
|===

The three wall-time phases sum to `totalWallSeconds` apart from clock precision. A solve completed without
numerical iterations reports `0.0` for `numericalSolveWallSeconds`. Later calls such as `values`,
`evaluate`, persistence and output are not included. `driverProcessCpuSeconds` is `None` when Java
cannot provide it.

[#_progress_and_cooperative_stopping_continuous_models]
=== Progress callbacks and stopping (continuous models)

[source,scala]
----
import com.github.vbmacher.spark_lp.{SolveControl, StagnationConfig}
import scala.concurrent.duration._
import java.util.concurrent.atomic.AtomicBoolean

val stop = new AtomicBoolean(false) // another driver thread can call stop.set(true)
val result = model.solve(SolveConfig(
  control = SolveControl(
    timeLimit = Some(20.minutes),
    shouldStop = () => stop.get(),
    onProgress = { event =>
      event.iterate.foreach { m =>
        println(s"iteration=${event.iteration} objective=${m.objectiveValue} " +
          s"primal=${m.primalResidual} gap=${m.dualityGap}")
      }
      event.work.foreach { w =>
        println(s"phase=${event.phase} completed=${w.completed} residual=${w.residual}")
      }
    },
    stagnation = Some(StagnationConfig(patience = 10)))))
try {
  println(s"status=${result.status} reason=${result.stopReason} candidate=${result.candidate}")
  if (result.candidate.available && result.candidate.feasible) {
    // Read or persist result.value(x) / result.values(amount) here.
  }
} finally result.close()
----

`SolveControl` applies to continuous solves. `timeLimit` starts after model compilation and excludes result
reconstruction. `shouldStop` and `onProgress` run synchronously on the driver, so keep them fast. An
exception from either callback fails the solve after cleanup. Stagnation detection is disabled unless
`stagnation` is set.

Progress events use these phases:

[cols="1,3",options="header"]
|===
|Phase |Meaning
|`Initialization` |Create the first numerical state.
|`SystemSetup` |Prepare the selected linear-system method.
|`InnerSolve` |Solve one linear system.
|`OuterIteration` |Finish one optimization iteration.
|===

Every `SolveProgress` has `phase`, `iteration` and `elapsedSeconds`.

[cols="2,3",options="header"]
|===
|Field |Meaning
|`iterate.objectiveValue` |The current objective in the model's original minimize/maximize direction.
|`iterate.primalResidual` |A normalized measure of constraint error.
|`iterate.dualResidual` |A normalized measure of optimality error.
|`iterate.dualityGap` |The difference between the current primal and dual objective estimates.
|`work.completed`, `work.total` |Completed and, when known, total setup or inner-solve work units.
|`work.residual` |The numerical error of the current inner solve.
|===

Stop checks occur between solver operations; they cannot interrupt an active Spark task or compiled-library
operation.
`maxIterations` returns `IterationLimit`. A time limit, `shouldStop`, or stagnation rule returns `Stopped`
with `TimeLimit`, `UserRequested`, or `NoProgress`. The solution retains the best completed feasible
assignment when one exists. Always check `candidate.available` and `candidate.feasible`; a stopped result
does not imply optimality. Use `MipControl`, described below, for integer models.

The xref:algorithm.adoc#_opt_in_progress_policy[opt-in progress policy] describes how stagnation windows
compare successive iterations.

== Solve-time controls and tuning

=== Prioritized objectives

`model.solvePriorities(...)` solves objectives in order. It optimizes the first objective, keeps that
result within an allowed tolerance, then optimizes the next objective. All objectives use the model's
`Minimize` or `Maximize` direction.

[source,scala]
----
val priorities = model.solvePriorities(Seq(
  LpPriority(cost, absoluteTolerance = 1e-6),
  LpPriority(emissions)))
try {
  if (priorities.complete) {
    val finalSolution = priorities.stages.last.solution.get
    finalSolution.values(priorities.copied.variables(production)).show()
  }
} finally priorities.close()
----

Each `LpPriority` accepts `absoluteTolerance` and `relativeTolerance`. After an optimum `z`, the next stage
may worsen that objective by at most
`absoluteTolerance + relativeTolerance * abs(z)`. `z` includes the objective constant.

The operation uses a copy and does not modify the source model. `priorities.complete` is true only when all
stages succeed. Inspect each stage's `solution.status` and `error`. Close the `LpPriorityResult`; it owns all
stage solutions.

=== Continuous relaxation

A continuous relaxation lets variables declared as `Integer` or `Binary` take fractional values for one
solve:

[source,scala]
----
val relaxed = model.solve(SolveConfig(relaxIntegrality = true))
----

`relaxed.isRelaxation` is true. The original model remains unchanged. Integer bounds are rounded inward to
whole values before relaxation, and binary bounds remain within `[0, 1]`. A fractional result is not a
valid integer assignment. Use the relaxation objective as a bound on the integer optimum, not as proof
that the integer model is optimal or unbounded. If the relaxation is proven infeasible, the integer model
is also infeasible.

=== Explicit rounded reports

`solution.rounded(LpRounding(integerTolerance = 1e-6, boundTolerance = 1e-8))` returns a read-only view
with `value(variable)` and `values(variableSet)`. It rounds an integer or binary value when it is within
`integerTolerance` of a whole number, then rounds any value within `boundTolerance` of a bound.

Rounding does not change `solution`, and the rounded view has no status or objective. Rounded values may
violate constraints; validate them before using them as an assignment. The view is valid only while its
source `LpSolution` is open.

[#_warm_starts_and_mip_starts]
=== Initial values for a solve

A start supplies initial variable values to a solve. It can reduce work, but it does not change the model
or guarantee a faster solve.

[cols="2,3",options="header"]
|===
|API |Purpose
|`model.start(Seq(x -> 1.0, items("a") -> 2.0))` |Create a start from local `LpVariable` objects and values.
|`model.start(valuesRdd, LpStartConfig(...))` |Create a start from distributed `LpCandidateValue` records.
|`solution.asStart()` |Copy the retained assignment from a solution into an independent start.
|`SolveConfig(start = Some(start))` |Pass the start to the solver.
|===

Starts belong to the model that created them. Duplicate variables, variables from another model and
non-finite values are rejected. Partial starts are allowed by default; set `allowPartial = false` to
require every variable. `repairBounds = true` clips values to bounds and rounds near-integral values.
`requireFeasible = true` accepts only a complete assignment that satisfies the original model.

`solution.start` reports `Accepted`, `Repaired`, `Rejected` or `Unsupported`, plus whether the start was
complete, feasible, used for initialization, or installed as the initial feasible integer assignment.
Acceptance does not mean the supplied values are optimal. A start created by `model.start` or
`solution.asStart()` owns cached data and must be closed.

[source,scala]
----
val initial = model.start(Seq(x -> 1.0, y -> 0.0))
try {
  val result = model.solve(SolveConfig(start = Some(initial)))
  try {
    println(result.start)
    println(result.objectiveValue)
  } finally result.close()
} finally initial.close()
----

See xref:benchmarks.adoc[benchmark methodology] for start/no-start comparisons that include construction
and validation time. Initial values can reduce solver work and can also increase total elapsed time.

[#_mip_progress_and_cooperative_stopping]
=== MIP progress callbacks and stopping

MIP means mixed-integer program: a model containing `Integer` or `Binary` variables. Configure the complete
integer search with `MipControl`:

[source,scala]
----
import scala.concurrent.duration._

val config = SolveConfig(mip = MipConfig(control = MipControl(
  timeLimit = Some(30.seconds),
  shouldStop = () => cancelled,
  onProgress = event => println(event))))
----

The time limit begins after model compilation and excludes result reconstruction. Progress events report
processed and open search nodes (subproblems created by fixing integer choices), elapsed time, the best
feasible integer objective, the best possible objective still allowed by unfinished search, and the
remaining absolute and relative gaps. Callbacks run on the driver.

Stopping retains the best verified feasible integer assignment, if one exists. Check
`candidate.available` and `candidate.feasible` before reading values. Stop checks cannot interrupt an
active Spark task or compiled-library operation.

=== MIP search tuning

Enable cuts, strong branching and concurrent nodes independently through `MipConfig.search`:

[source,scala]
----
val result = model.solve(SolveConfig(mip = MipConfig(
  maxNodes = 1000,
  search = MipSearchConfig(
    cuts = MipCutsConfig(enabled = true, maxRounds = 2, maxCutsPerNode = 20, maxCuts = 100),
    strongBranching = StrongBranchingConfig(enabled = true,
      maxCandidates = 4, maxIterations = 5, maxProbes = 100),
    parallelNodes = 2,
    maxConcurrentLocalBytes = 1024L * 1024 * 1024))))
try println(result.mip.map(_.search)) finally result.close()
----

[cols="2,3",options="header"]
|===
|Setting |Effect
|`cuts` |Add constraints that remove fractional binary solutions without removing feasible binary solutions. Disabled by default.
|`strongBranching` |Temporarily solve both choices for candidate integer variables before selecting the next variable. Disabled by default.
|`parallelNodes` |Maximum number of simultaneous continuous subproblem solves. Default `1`.
|`maxConcurrentLocalBytes` |Maximum estimated driver-side numerical storage for simultaneous relaxations. Default 1 GiB.
|===

`maxNodes` counts launched search nodes. Extra continuous solves for cuts and strong branching do not add
to that count. `solution.mip.get.search` reports continuous subproblem solves, cut rounds, added cuts,
strong-branching probes, peak concurrency and estimated concurrent numerical storage.

More cuts, probes or parallel nodes can increase work and memory. Measure the complete solve under the
application's Spark scheduling and data sizes. `MipSearchConfig()` restores the serial baseline.

The xref:algorithm.adoc[algorithm guide] defines cut validity, bound acceptance and memory estimates. The
xref:benchmarks.adoc[benchmark methodology] defines comparisons of individual options and all
combinations at equal tolerances.

=== Presolve and reconstruction

Presolve simplifies a model before numerical optimization while preserving its solutions.

[cols="2,3",options="header"]
|===
|Configuration |Behavior
|`PresolveConfig()` |Use `Basic`, the default. Remove fixed variables and empty constraints, merge duplicate equalities, and infer integer bounds when required.
|`PresolveConfig(effort = PresolveEffort.Full)` |Also propagate bounds, fix variables determined by one equality, and substitute eligible free continuous variables.
|`PresolveConfig(enabled = false)` |Disable optional presolve. Required conversion of fixed variables and empty constraints still occurs.
|===

`solution.presolve` reports original and remaining variable and constraint counts, numerical-solver
dimensions, fixed variables, changed bounds and substitutions. Public values and constraint diagnostics
are reconstructed in the original model's coordinates. Every `solve()` recomputes presolve from the
current model and current Spark inputs.

See xref:benchmarks.adoc[benchmark methodology] for presolve performance measurements.

=== Integer bounds inferred from constraints

The built-in integer solver requires finite search bounds. You may declare them directly or let presolve
derive them from linear constraints. For example, `amount <= 12.5` gives an integer variable the effective
upper bound `12`.

`BoundInferenceConfig(maxPasses, maxLocalChanges, tolerance)` limits this propagation. Inferred bounds are
used only for that solve; the declared variable remains unchanged. The solver never substitutes an
arbitrary finite cap. If it cannot derive a finite interval for a constrained integer variable, the solve
fails with an unsupported-model error. A contradiction established during inference returns `Infeasible`.

[source,scala]
----
val model = LpProblem("integer capacity", Maximize)
val amount = model.variable("amount", category = Integer)
model += lpSum(amount)
model += (amount <= 12.5)
val result = model.solve()
try println(result.value(amount)) finally result.close() // 12
----

== Sensitivity and diagnostics

=== Original model inspection

`val view = model.inspect` returns an `LpModelView`: a read-only view of the model as declared, before
presolve or solver-specific conversion.

[cols="2,3",options="header"]
|===
|API |Data
|`view.variableDeclarations` |Local variable-set metadata: IDs, names, variable types and bounds.
|`view.constraintDeclarations` |Local constraint metadata: IDs, names and comparison directions.
|`view.variables` |One distributed record per individually declared or keyed variable.
|`view.constraints` |One distributed record per individually declared or grouped constraint.
|`view.coefficients` |Distributed constraint coefficients.
|`view.objectiveCoefficients` |Distributed linear-objective coefficients.
|`view.diagonalCoefficients`, `view.quadraticFactors` |Distributed quadratic-objective data.
|`view.statistics()` |Exact counts of variables, constraints and nonzero coefficients.
|===

Creating the view performs no Spark action. Reading expanded data or statistics does. The view keeps the
declarations present when `inspect` was called, but it shares lazy DataFrame and Dataset inputs with the
model. Store changing inputs in stable storage when inspection must read an unchanging copy.

=== Independent candidate validation

Use candidate validation to check values produced outside the solver:

[source,scala]
----
val values = model.candidateValues(Seq(x -> 2.0, amount("a") -> 1.0))
val report = model.validateCandidate(values)
try {
  println(report.feasible)
  report.violations.show()
} finally report.close()
----

The assignment must contain exactly one finite value for every model variable. Missing, duplicate or
foreign variable IDs make the report infeasible. `report.violations` contains bound, integrality and
constraint violations; `report.maxViolation` is the largest absolute violation.

`CandidateValidationConfig` defaults to `1e-8` for bounds and constraints and `1e-6` for integrality.
`relaxIntegrality = true` skips integer-value checks but still enforces all bounds and constraints.
Validation also computes the objective for a complete finite assignment. It does not optimize or claim
optimality. Close the report after its distributed data has been consumed.

=== LP shadow prices

For an optimal continuous linear model, the nullable `dual` column in `solution.constraints` estimates
how the optimal objective changes when that constraint's right-hand side changes slightly. This is also
called a shadow price.

For minimization, an active `>=` constraint usually has a nonnegative shadow price and an active `<=`
constraint a nonpositive one. Maximization reverses those signs. Equality prices may have either sign.
`dual_note` explains why a value is absent. Prices are absent for stopped, infeasible, quadratic and
integer solves, and for constraints whose individual price cannot be recovered after presolve. They are
local numerical sensitivity estimates, not guarantees for large changes.

=== LP reduced costs

`solution.reducedCost(variable)` returns `Option[Double]` for one variable.
`solution.reducedCosts(variableSet)` returns the declaration DataFrame with a nullable
`lp_reduced_cost` column.

For a minimization model, a variable at its lower bound normally has a nonnegative reduced cost, a variable
at its upper bound a nonpositive one, and a variable strictly between its bounds a value near zero.
Maximization reverses the bound signs. Reduced costs are available only when the solution has the required
optimal continuous-linear shadow prices. Fixed variables and variables affected by unavailable prices
return `None` or `null`.

=== Integer optimality gaps

An integer solver maintains:

* the incumbent: the best feasible integer objective found so far;
* the global bound: the best possible objective still allowed by unfinished search.

`MipConfig(absoluteGapTolerance = 0.0, gapTolerance = 1e-9)` accepts the incumbent when either remaining
gap is within its limit. For minimization, the absolute gap is
`max(0, incumbent - globalBound)`; maximization reverses the subtraction. The relative gap divides the
absolute gap by `max(1, abs(incumbent))`.

`solution.mip` exposes the incumbent, global bound, both gaps, processed and open node counts, search
statistics and termination reason. A gap is absent until both a feasible incumbent and a finite global
bound exist. `GapTolerance` means a positive configured gap was accepted; `SearchExhausted` means no
unresolved search nodes remain.

== Interchange and external solvers

=== Portable model and component data

Portable data is the public, Spark-distributed representation used by exporters and solver adapters.

[cols="2,3",options="header"]
|===
|API |Result
|`LpPortableModel.fromView(model.inspect)` |The complete model as schema-versioned metadata and distributed coefficients.
|`LpPortableModel.variable(x)` |One expanded variable record.
|`LpPortableModel.expression(expression)` |Portable linear-expression data.
|`LpPortableModel.constraint(constraint)` |Portable constraint data.
|`data.toProblem(maxLocalRows = 10000)` |A new `LpProblem` plus mappings from portable IDs to its variables and constraints.
|===

The format preserves model-local IDs, encoded keys, names, bounds, variable types, linear coefficients and
quadratic terms. It does not preserve original application columns or executable Spark plans. Imported
variable data therefore exposes encoded `lp_key` values instead of the source DataFrame schema.

Import collects constraint metadata up to `maxLocalRows`; variable records and coefficients remain
distributed. The imported model is independent of the source model. `LpSolutionData` can carry result
metadata and values, but importing it does not independently prove feasibility or optimality.

=== JSON model interchange

`LpJson` writes portable data as a directory containing JSON-lines partitions:

[source,scala]
----
LpJson.write(model, "s3://bucket/models/plan")
val document = LpJson.read("s3://bucket/models/plan")
val imported = document.model.toProblem()
----

Pass `solution = Some(LpSolutionData.fromSolution(result))` to include result data. Imported result
metadata has `solutionMetadataVerified = false`; validate imported values before relying on them.

Schema `1` preserves IDs, encoded keys, display names, bounds, variable types, the objective, constraints
and squared-expression terms. It excludes application-specific DataFrame columns, closures, credentials and
Spark execution plans. Unknown schemas and invalid references are rejected.

The destination is a Hadoop filesystem directory, not a single file. Existing destinations require
`overwrite = true`. Large model data remains partitioned. Keep lazy inputs stable until the write action
finishes.

=== Explicit algebra rendering

[cols="2,3",options="header"]
|===
|API |Output
|`LpAlgebra.preview(model.inspect, maxLines = 80)` |A bounded text preview with an exact `TRUNCATED` count.
|`LpAlgebra.write(model.inspect, writer)` |The complete model written to a caller-owned `Writer`.
|`LpAlgebra.expression(expression, maxTerms)` |One expression, with an explicit term limit.
|`LpAlgebra.constraint(constraint, maxTerms)` |One constraint, with an explicit term limit.
|===

Rendering includes the optimization direction, objective constant, constraints, bounds, variable types and
quadratic terms. It performs Spark actions and orders output deterministically. The text is for review; it
is not an LP or MPS file accepted by external solvers.

=== LP-file export

`LpExport.lp(model.inspect, path)` writes a linear model in CPLEX-style LP syntax to a local UTF-8 file.
Quadratic and SOS models are rejected.

The default `ExportNaming.Normalized` uses deterministic `vN` variable names and `rN` constraint names.
The returned closeable mapping converts those names back to original model IDs and names.
`ExportNaming.Original` instead requires every original name to be a unique, nonreserved ASCII identifier
of at most 200 characters.

The parent directory must exist. Existing files require `overwrite = true`. Export performs Spark actions;
keep lazy inputs stable until the export and any mapping reads finish, then close the mapping.

=== MPS-file export

MPS means Mathematical Programming System, a text format for optimization models.
`LpMps.write(model.inspect, path)` writes a free-format (whitespace-delimited) MPS file on the driver
filesystem. It returns the same closeable name mapping as LP export. Quadratic and SOS models are rejected.

[cols="2,3",options="header"]
|===
|Option |Behavior
|`naming = ExportNaming.Normalized` |Use deterministic generated names and return mappings to original IDs. This is the default.
|`naming = ExportNaming.Original` |Use original unique ASCII names of at most 200 characters.
|`relaxIntegrality = true` |Export integer and binary variables as continuous variables while preserving their effective bounds.
|`overwrite = true` |Replace an existing destination after a complete temporary file has been written.
|===

The file includes `OBJSENSE`, so minimization and maximization are preserved. The free objective row
(the MPS record containing objective coefficients) stores the negative objective constant in `RHS`
(the right-hand-side section); an MPS reader that ignores these extensions will not preserve the
full objective. See the
https://docs.gurobi.com/projects/optimizer/en/current/reference/fileformats/modelformats.html[MPS format reference].

=== MPS-file import

`LpMpsImport.read(path, options)` reads a local UTF-8 MPS file and returns:

* `model`: a normal `LpProblem` that can be edited, inspected and solved;
* `variables`: a `Map[String, LpVariable]` indexed by MPS column name;
* reconstructed constraints indexed by original MPS row (constraint) name.

Import does not solve the model or invent missing bounds. The default optimization direction is minimize;
an `OBJSENSE` section or `MpsReadOptions.objectiveSense` can select maximize. Repeated coefficients are
added, and absent coefficients or right-hand sides are zero.

Supported bound records are `LO`, `UP`, `FX`, `FR`, `MI`, `PL`, `LI`, `UI` and `BV`. Supported range rows
are reconstructed as lower and upper constraints. Unsupported quadratic, SOS and semi-continuous records
(variables that are either zero or within a nonzero interval) are rejected with file, line and section
information.

Parsing stores declarations and coefficient records on the driver. Defaults limit input to 64 MiB,
100,000 variables, 10,000 constraints and 1,000,000 coefficient records. Change these limits explicitly
with `MpsReadOptions` only when the driver has enough memory.

[source,scala]
----
import java.nio.file.Paths
import org.apache.spark.sql.SparkSession
import com.github.vbmacher.spark_lp.dsl._

implicit val spark: SparkSession = SparkSession.builder().master("local[*]").appName("mps").getOrCreate()
val imported = LpMpsImport.read(Paths.get("model.mps"))
val result = imported.model.solve()
try imported.variables.toSeq.sortBy(_._1).foreach { case (name, variable) =>
  println(s"$name = ${result.value(variable)}")
} finally { result.close(); spark.stop() }
----

=== Custom solver adapters

Use `model.solve(adapter, LpAdapterOptions(...))` to solve through an application-provided
`LpSolverAdapter`. `model.solve(SolveConfig(...))` continues to use spark-lp's built-in solver.

An adapter declares `LpSolverCapabilities` and implements
`prepare(view, options): LpAdapterSession`. The session's `solve()` returns an `LpAdapterResult`; `close()`
must be safe to call more than once. spark-lp validates returned variable IDs, finite values, bounds,
integrality, original constraints and objective value before creating the public `LpSolution`.

`LpAdapterOptions.maxVariables`, `maxConstraints` and `maxNonzeros` limit the model size transferred to an
adapter. Unsupported model features are rejected before preparation. Adapter sessions and local solver
models stay on the driver and must not be captured in Spark executor closures.

Extend `LpCommandAdapter` for a solver invoked as a child process. Implement:

* `command(modelFile, solutionFile, options)` as a sequence of arguments, not a shell command;
* `parse(solutionFile, mapping, options)` with explicit input limits.

The base class handles LP export, generated-name mappings, temporary files, cancellation, timeouts and
bounded process logs. `LpCommandOptions(retainArtifacts = true)` keeps temporary files and reports their
paths; otherwise they are deleted when the session closes.

Executable examples are in
`spark-lp/src/test/scala/example/adapters/AdapterConformanceSuite.scala`.

=== Native solver sessions

`model.prepareNative(adapter, options)` returns either `LpUnsupported` or an `LpNativeSession`. A native
session exposes the external solver's direct API and keeps one prepared solver model for repeated solves.

[cols="2,3",options="header"]
|===
|API |Purpose
|`session.setParameter(name, value)` |Set an external-solver parameter.
|`session.parameter(name)` |Read an external-solver parameter.
|`session.information(name)` |Read external-solver information after a solve.
|`session.callback(handler)` |Register an external-solver callback.
|`session.readSolution(path)` |Load an external-solver solution or start file.
|`session.writeSolution(path)` |Write the latest external-solver solution.
|`session.solve()` |Solve the prepared model and return an `LpSolution`.
|`session.isCurrent(result)` |Test whether a result matches the current parameters, callback and imported solution.
|===

Unsupported operations return `LpUnsupported`. Preparing a session prevents edits to the `LpProblem` until
the session closes. Use every session method, including `close()`, from the driver thread that created it.
Do not serialize the session or capture it in executor closures. Finish Spark actions on mappings and
results before closing.

`HighsPythonAdapter` provides native LP and MIP access through an existing Python `highspy` installation or
the HiGHS module bundled with SciPy. spark-lp installs neither package. The adapter supports HiGHS
parameters, information queries, callbacks, LP shadow prices and reduced costs, and HiGHS solution files.
It does not support quadratic or SOS models.

The HiGHS bridge runs as a child process with explicit limits on the driver. `LpAdapterOptions.timeLimit`
and `shouldStop` control solve execution. Startup and operation timeout default to 60 seconds; process log and response-size
limits are configurable. An interrupted native session must be closed and prepared again.

[source,scala]
----
val adapter = new HighsPythonAdapter()
val session = model.prepareNative(adapter).fold(
  unsupported => throw new IllegalArgumentException(unsupported.detail), identity)
try {
  session.setParameter("presolve", "on").fold(
    unsupported => throw new IllegalArgumentException(unsupported.detail), identity)
  session.callback(event => println(event.message))
  val result = session.solve()
  println(result.objectiveValue)
  println(session.information("simplex_iteration_count"))
  session.writeSolution(java.nio.file.Paths.get("solution.txt"))
} finally session.close()
----

Further examples are in `spark-lp/src/test/scala/example/adapters/NativeSessionSuite.scala`. Backend API
details and callback semantics are defined by the
https://ergo-code.github.io/HiGHS/stable/interfaces/python/[HiGHS Python documentation] and
https://github.com/ERGO-Code/HiGHS/blob/master/examples/call_highs_from_python.py[HiGHS callback examples].
